# ADR-0002: System architecture (as-built, reverse-engineered)

- Status: Accepted
- Date: 2026-08-12
- Deciders: project lead (confirmed via Step 4.0 architecture elicitation)

## Context

This is a brownfield Spring Boot tutorial repo: a working Student CRUD REST API already exists (`Student` entity, `StudentRepository`, `StudentService`, `StudentController`, `StudentConfig`) backed by PostgreSQL via Spring Data JPA. This ADR documents the architecture **as it actually is today**, reverse-engineered from the codebase and confirmed with the user during Step 4.0 — it does not propose a target architecture, and the "keep as-is" gaps below are accepted tutorial-scope limitations, not defects to schedule.

## Decision

The system's high-level architecture, across the six dimensions:

- **Runtime & delivery** — a single Spring Boot 3.0.6 jar (Java 21), built via Maven (`mvnw`), deployed as one process to a Linux server/cloud container. No containerization manifest (Dockerfile/compose) exists in-repo.
- **State & data** — PostgreSQL is the sole datastore, accessed via Spring Data JPA (`StudentRepository extends JpaRepository<Student, Long>`). Connection configured in `src/main/resources/application.properties`. `spring.jpa.hibernate.ddl-auto=create-drop` means Hibernate derives and recreates the schema from the `Student` entity on every app start and drops it on shutdown — there is no migration tool (Flyway/Liquibase) and no persisted schema history.
- **Interfaces & contracts** — one synchronous REST resource, `StudentController`, mounted at `api/v1/student` (GET list, POST create, PUT `/{studentId}` update, DELETE `/{studentId}`). No OpenAPI/Swagger spec, no API versioning strategy beyond the literal `v1` path segment (not enforced anywhere else).
- **Execution model** — fully synchronous request/response via Spring MVC. No async jobs, message queues, or scheduled tasks. `StudentConfig` seeds two rows via a `CommandLineRunner` at application startup only (one-shot, not recurring).
- **Trust & access** — no authentication or authorization layer. No `spring-boot-starter-security` dependency in `pom.xml`. Every endpoint under `api/v1/student` is open to any caller.
- **Operability** — default Spring Boot console logging only, with `spring.jpa.show-sql=true` for SQL echo. No metrics or tracing dependency (no Actuator, no Micrometer). No structured exception handling: `IllegalStateException`s thrown from `StudentService` (duplicate email, missing id) propagate as generic framework 500 responses rather than mapped HTTP status codes.

## Alternatives considered

- Flyway/Liquibase-managed schema instead of `ddl-auto=create-drop`: not adopted — out of scope for a tutorial; flagged below as a gap for any real deployment.
- Spring Security (basic auth / JWT) for the REST endpoints: not adopted — tutorial intentionally has no auth; flagged below.
- `@ControllerAdvice`/`@ExceptionHandler` for structured error responses: not adopted — errors currently bubble up as opaque 500s; flagged below.

## Consequences

- Positive: architecture matches exactly what is in the repo today — no drift between this ADR and the running code; simple enough that a beginner can trace every request end-to-end (Controller → Service → Repository → Postgres).
- Negative: schema loss on every restart (`create-drop`), no auth boundary, no observability beyond console logs, no OpenAPI contract for consumers.
- Reversible? Yes, at low cost for a codebase this size — each gap (migrations, auth, exception mapping, Actuator) is additive and independently adoptable without restructuring the existing Controller/Service/Repository layering.

## Flagged gaps

- No migration tooling — schema is fully regenerated by Hibernate on every start (`ddl-auto=create-drop`); any real deployment needs Flyway/Liquibase before this is safe against data loss.
- No authentication/authorization — every endpoint is unauthenticated; acceptable for a local tutorial, not for any networked deployment.
- No structured error handling or observability — no `@ControllerAdvice`, no Actuator/metrics/tracing; failures surface as generic 500s with no correlation id or health endpoint.
- No containerization manifest (Dockerfile/docker-compose) despite the "containerized... deployed to a Linux server/cloud container" runtime intent recorded in Step 4.0 — nothing in-repo currently builds or runs a container image.
- No documented Postgres bootstrap/start command in-repo (credentials are hardcoded in `application.properties`, no docker-compose service) — recorded as a `[NEEDS CLARIFICATION]` entry in `docs/config/stack-smoke.md`.
