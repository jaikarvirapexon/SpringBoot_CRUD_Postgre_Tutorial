### Evidence per TC (real server, real Postgres, no mocks)

- **TC-01**: `GET http://127.0.0.1:8080/api/v1/student/1` → `200`, body `{"id":1,"name":"Mariam","email":"mariam.jamal@gmail.com","dob":"2000-01-05","age":26}`. Matches list-endpoint shape.
- **TC-02**: `GET http://127.0.0.1:8080/api/v1/student/999` → `404`, empty body. Not a 500 — no `IllegalStateException` propagation observed in server log.
- **TC-03**: `GET http://127.0.0.1:8080/api/v1/student/abc` → `400`, body `{"timestamp":"2026-08-12T21:51:30.592+00:00","status":400,"error":"Bad Request","message":"Failed to convert value of type 'java.lang.String' to required type 'java.lang.Long'; For input string: \"abc\"","path":"/api/v1/student/abc"}` — Spring's default `MethodArgumentTypeMismatchException` handling, no custom validation code, as ADR-1/T-02 specified.
- **TC-04**: `GET .../student/-1` → `404`; `GET .../student/0` → `404`. Both numeric, both resolve to the not-found path, not a 400.
- **TC-05**: `GET .../student/999` response headers show `Content-Length: 0` — the body is completely empty (see note below), containing zero of the forbidden fields (no stack trace, no exception class name, no internal identifier).

### Note on TC-05 (informational, not a failure)

TC-05's `then` clause anticipates "Spring's default error JSON fields (status, error, message, timestamp, path)" in the 404 body. Actual behavior: `ResponseEntity.notFound().build()` (per ADR-1) returns a **fully empty** body (`Content-Length: 0`) — it never reaches `BasicErrorController`, so none of those 5 fields are actually present either. This is a stricter negative than the then-clause's literal wording implied (a whitelist assertion: the body must contain *only* those fields, which an empty body trivially satisfies since it contains none of the forbidden ones and none of the field superset). `README.md:589` explicitly documents this exact empty-body behavior as intended, so it is not a documentation/implementation drift — the then-clause phrasing in `docs/test-cases/STU-01.json` is marginally imprecise and could be tightened to "no JSON error fields are required to be present; the response contains no forbidden field types" in a future TC revision. Not raised as a bug block because it does not represent a defect — recorded here for traceability only.
